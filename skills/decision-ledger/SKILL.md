# Decision ledger protocol

Use the `decision_ledger` tool for session decision state. Session IDs (short display tokens such as `ABC`) are not durable ADR UUIDs; never fabricate either IDs or digests, and never bypass the extension's safe operations.

## Durable ADRs (bounded core)

The package also exposes a separate durable ADR core in `src/durable.ts`. Its experimental native v1 uses the official MADR 4.0 bare-minimal body and top-level MADR `status`; only Pi-specific UUID, digest, version, and supersession links live under `x-pi-decision-ledger`. It does not generate Follow-ups. Durable imports preserve unknown frontmatter, sections, comments, anchors, line endings, and final-newline style; updates rewrite only owned fields and recognized sections, and refuse ambiguous envelopes, fences, or boundaries rather than guessing. Import recomputes and checks `semantic-digest/v1` (canonical UTF-8/JCS payload); the exact-byte source fingerprint is separate and is not identity. V1 is still experimental: discard and regenerate experimental artifacts rather than inventing migration machinery.

Durable identity is a lowercase UUIDv4. Accepted ADRs are immutable: substantive replacement creates a new UUID and a forward `supersedes` list, while lifecycle/backlink metadata may be updated. Validate record sets for duplicate, unknown, self-referential, and cyclic supersession IDs. This is intentionally a small ADR format/core, not a repository-wide ADR platform.

## Repository-backed durable ADRs

`src/durable-repository.ts` adds filesystem library primitives over that core; these are not session tool actions or automatic synchronization. Checkout provenance is copied and frozen, with a canonical repository root and no symlinks below it. Respect its authority rule: session ledger state is authoritative only until a repository ADR draft exists for a decision. Once that file exists, the repository file is authoritative, and any value you hold in the session is a working copy carrying the durable UUID, repository provenance, base semantic digest, exact-byte source fingerprint, and original source. Never treat session state as newer than the file, and never assume that moving a decision into the repository accepted it.

A repository draft is still mutable, but only through conflict-checked publishing, and its UUID stays stable through edits and later acceptance. Take a checkout with `checkoutDurableAdr`, then publish edits with `publishDurablePatch`. Publishing rereads the authoritative file and requires exact bytes matching the checkout base. Any difference refuses the write, even a semantically irrelevant one such as an added comment. There is no merge and no overwrite. The refusal returns structured conflict data holding the base, the observed file state (invalid UTF-8 as base64), your patch, and the proposed source; write failures also retain the intended edit. Report the conflict and keep those edits rather than retrying blindly. Checking is optimistic, not a filesystem compare-and-swap: callers must coordinate concurrent writers and directory changes because an external edit can race the final check and rename. Recovery is manual and explicit: `reloadDurableCheckout` gives a fresh checkout, and you decide what to republish; do not loop on publish attempts.

Use `createDurableAdrFile` to write a validated draft; it stages the complete file and publishes exclusively, never replacing an existing file. It does not enforce a review policy. Use `acceptDurableAdr` for the explicit internal `draft` -> `accepted` transition, serialized as top-level MADR `status: proposed` -> `status: accepted`. It rereads, imports and verifies the ADR and changes only that status field; an equivalent manual YAML edit is recognized on the next import and the file is left untouched. Acceptance is only this lifecycle transition: there is no governance, reviewer role, or PR policy here.

Do not invent behavior that is not settled yet. Rejected or abandoned durable lifecycle states (only discarding an unchanged draft exists), dependency graphs between ADRs, repository browsing, and implementation evidence are all out of scope; do not simulate them with these primitives.

## Promotion to repository ADRs

Promotion is explicit, selective, and always user-driven. Never promote automatically, and never treat any rule as a significance classifier. Recommend promotion when a decision has lasting architectural weight: it constrains future work, is expensive to reverse, or people outside this session will need its reasoning. Leave everything else in the session ledger—routine implementation choices, session-local preferences, and decisions whose value expires with the conversation. When unsure, suggest it once and let the user decide.

Only `open`, `proposed`, and `resolved` decisions can be promoted. A promoted decision cannot be promoted again, and an actively explored decision must first finish with `/decision return` or `/decision exit`.

Promote with an explicit ordered source set. Group only decisions the user treats as one commitment; split when sources would need separate acceptance, would be superseded independently, or would leave a reader unable to tell which constraint applies. Prefer one-to-one promotion when in doubt. The optional slug is lowercase kebab-case; otherwise it is derived from the reviewed solution-oriented title.

For several sources, and whenever a single source deserves better wording than its raw record, synthesize one coherent ADR. Use the MADR 4.0 bare-minimal body exactly: `# <solution-oriented title>`, `## Context and Problem Statement`, `## Considered Options` (a `- ` list), `## Decision Outcome`, and `### Consequences`. State the chosen option and why in Decision Outcome; express meaningful positive and negative consequences clearly. Do not add Follow-ups, Decision Drivers, Confirmation, More Information, or per-source blocks. Follow-up work belongs in issues, implementation manifests, or session records. Session decision IDs may appear only in provenance, never as the structure of the prose.

Call `decision_ledger` action `promote_adr` once with the ordered `ids`, exact envelope-free `markdown`, and optional `slug` and `repository`. This opens mandatory editable review for the user and writes only after approval; cancellation writes nothing and assigns no identity. `/decision promote` is a direct user-triggered convenience for deterministic one-source promotion only. Multi-source promotion always requires your synthesized Markdown. Never bypass the exact review.

The ADR goes to the Git repository containing the working directory. If the working directory is not inside a Git repository, or the ADR belongs to another repository, the user must pass `--repo <path>` naming a Git repository root; never guess among nested repositories.

The command opens the exact ADR Markdown for review. The reviewed text is the only input to validation, the semantic digest, and the written file. Cancelling the review or failing validation writes nothing, assigns no durable UUID, and transfers no authority. On success the extension writes `decisions/<slug>.md` exclusively and creates a first-class registry entry carrying the UUID, repository provenance, base digest, exact-byte fingerprint, and frozen source IDs. From that moment the repository file is authoritative and session values are working copies.

Promotion creates a first-class ADR registry entry with a stable human slug and canonical UUID. Source decision IDs are provenance, not ADR handles; removing those decisions must not remove the registry entry. Use `/adrs` to discover ADRs and `/adr edit|reload|discard|accept <slug>` for all post-promotion operations. An exact UUID is a machine fallback. Never target ADR commands through a source decision ID.

Draft editing publishes only when the authoritative file still matches the checkout bytes. After a direct file edit, the user must run `/adr reload <slug>` to adopt it; never reload for them or retry in a loop. `/adr discard <slug>` deletes only an unchanged draft, removes its registry entry, and detaches surviving source decisions. `/adr accept <slug>` rereads and verifies before the proposed-to-accepted transition. Accepted ADRs are never discarded; they need a successor. Promotion does not change session decision lifecycle, and acceptance adds no governance, reviewer role, or PR policy.

## Identify decision-bearing points

A decision-bearing point is a choice, confirmation, preference, or unresolved trade-off that belongs to the user. Do not create ledger items for routine implementation details the agent can safely choose. When one or more user-resolvable points are present, call `decision_ledger` with an `add` action before presenting them; when there are two or more, use one `add` action containing all points so the batch is atomic.

Every new add item must include:

- `title`: a minimal meaningful phrase, preferably a few words, used as the stable compact display label
- `point`: the complete precise decision point; do not shorten it to fit a widget
- optional `lifecycle` and `record` only when the user already supplied or explicitly accepted that initial state or outcome

Omitting `lifecycle` creates an `open` item. Initial `proposed`, `resolved`, and `ignored` items require a complete five-field `record`; `deferred` may include a record; `open` must not include one. Exploration is never valid as an initial lifecycle because it requires a live conversation bookmark—use the `explore` transition instead. A proposed add item stores its exact canonical Markdown draft on that item, so multiple proposed items retain independent drafts through acceptance, exploration, revision, replay, and return. Add validation is atomic: one invalid item rejects the entire batch without items, IDs, drafts, or partial state.

Use the returned raw IDs when calling tools and commands. Human-facing Markdown and prose show IDs as code-like tokens such as `ABC` or `123`; the interactive TUI uses bracketed tokens such as `[ABC]`. Legacy snapshots without a title use their full point as the display-title fallback. Stored IDs, TypeBox fields, command arguments, completion values, and lookup keys stay raw; completion labels use the bracketed TUI form.

Accept terse replies such as “the first option” or “defer the rollout.” Interpret them against the current ledger, ask one concise clarification when needed, and do not silently choose for the user. Use `update` only for metadata (`title` and/or `point`); use explicit `resolve`, `accept`, `reject`, `defer`, `ignore`, or `reopen` actions for state changes. Canonical lifecycles are `open`, `proposed`, `resolved`, `deferred`, and `ignored`; exploration is only a bookmark. Never infer an initial outcome on `add`; use an initial non-open lifecycle only when the user's message already supplied or accepted it. `resolved` is the successful terminal state; `ignored` is a separate terminal lifecycle. `record.followUps` is the only follow-up metadata.

## Removal

Use `decision_ledger` action `remove` only after the user explicitly requests removal, and set `userRequested` to true only for that request. Pass one or more raw IDs in `ids`; removal is atomic and affects only the current branch. Never remove an actively explored decision. IDs are never reused, and earlier snapshots naturally retain removed items. For an interactive request, prefer `/decision remove <ID> [<ID> ...]`, which asks for confirmation.

## Focused exploration

When a decision needs investigation, use `decision_ledger` action `explore` when the user explicitly and unambiguously asks to explore a specific decision. If the target is ambiguous, ask one concise clarification rather than guessing. Only one focused exploration may be active. A direct `/decision explore <ID>` switches focus after safely exiting the previous exploration; `/decision exit` explicitly abandons the current focus. Unrelated prompts are still allowed while focus is active.

Starting exploration preserves an `open` or `proposed` lifecycle and adds a bookmark containing return metadata. A lightweight `proposed` item can enter focused exploration while retaining its record and Markdown proposal. `/decision exit` clears only the bookmark; it never restores a lifecycle from `origin` or clears proposal data. Cancellation, branch replay, and failed navigation must not finalize or discard that proposal. Starting or switching focus appends one concise, visible, durable transition containing the formatted ID, concise title, and full point. Successful starts do not also emit a transient yellow notification; actual errors still warn. Exiting and successful return append one corresponding cleared/resolved transition. On every LLM call, the extension derives focus from the live branch, removes an earlier hidden marker, and appends one final hidden marker only while focus is active. The marker names the ID, title, and point, disambiguates this/it/the decision/the proposal unless the current user message identifies another subject, and says that a recently resolved decision does not regain focus.

Only the focused decision receives a soft focus reminder on each agent turn. Keep work centered on its point, but do not reject unrelated work. Honor explicit requests to switch or exit. `/tree` changes conversation state, not files, and does not undo edits.

After investigating, use `decision_ledger` action `propose` with a minimal record for the focused item. In interactive TUI mode, `/decision return` shows an animated theme-aware `Summarizing decision and returning` widget immediately after valid Markdown review and before draft persistence/navigation; it is cleared on success, cancellation, errors, shutdown, reload, and early exits. It is not shown in headless modes and does not replace Pi's native follow-up loader.

Include all five fields:

- `decision`: the proposed decision or outcome
- `context`: why the decision was needed and relevant evidence
- `optionsConsidered`: the meaningful alternatives considered
- `consequences`: important effects and trade-offs
- `followUps`: concrete follow-up actions, or an empty list

Do not mark an explored item resolved in the proposal. Then ask the user to run `/decision return`. That command opens the latest compact Markdown record for review/editing, persists the exact valid reviewed draft while the item remains proposed, and adds it to branch context through a hidden custom message so Pi's summarizer can see it without an unwanted model turn or duplicate UI. It then navigates back with a narrowly focused complementary handoff. The handoff must not repeat the record's decision, context, options, consequences, or follow-ups. It asks only for additional evidence or references, unresolved caveats or risks, effects on other work, and immediate context needed to continue; if nothing additional exists, it gives one brief no-additional-context statement. The finalized record is written and resolved only after successful navigation. Successful return uses the reviewed record directly rather than parsing or regenerating it from the summary.

An open item may receive a lightweight proposal through `propose`; it has no exploration bookmark. Use `accept` to resolve it with its candidate record or `reject` to return it to `open` and clear candidate data. A lightweight proposal may later be explored without losing its record or Markdown draft. An explored proposal must go through exact Markdown review and `/decision return`; active exploration cannot be bypassed by disposition actions.

## Dashboard discipline

Use `decision_ledger` action `list` or `/decisions` to view the complete dashboard. When the user wants a fresh context without automatic compaction, use `/decisions new`: it starts a new session containing only an exact snapshot of the active branch ledger. Ordinary `/new` remains blank. Refuse the handoff while exploration is focused because its return bookmark belongs to the old session; the user must first use `/decision return` or `/decision exit`. `/decisions` includes resolved, ignored, and deferred rows so terminal items can be reopened. The bottom session widget is different: it shows only `open` and `proposed` rows, with open rows first, stable order within lifecycle groups, and a `Decisions: N/M completed` progress heading. N counts resolved and ignored; deferred is not completed. When exploration is focused, it shows only the focused row with its ID, concise title, and an `Exploring` indicator; other rows and a separate focus footer are hidden. Otherwise it displays concise titles and keeps no more than five decision rows; truncation is based on actual terminal width and occurs only at render time. If no actionable rows remain, the progress heading still appears.

The selector supports Enter for details and Esc/Ctrl+C to close. It also supports `e` explore, `a` accept/review, `x` reject, `i` ignore, `r` reopen, `f` defer, Delete to remove, and `?` help. Acceptance, rejection, ignoring, and removal are confirmed interactively. Invalid actions report a concise reason without closing the selector. Destructive transitions are refused while exploration is active; use `/decision return` or `/decision exit` first.

The extension layers decision-only autocomplete over Pi's provider during TUI session setup. It intercepts `/decision` subcommands and `explore`/`remove` ID positions even for forced Tab completion, ranks `return` before `remove` for `re`, returns only matching current IDs while excluding already-selected remove IDs, and keeps raw completion values with bracketed `[ID]` labels and concise title descriptions. ID contexts suppress filesystem suggestions; unrelated commands, normal text, and explicit paths delegate unchanged.

Interactive details show a compact lifecycle symbol/state and bracketed ID header, then the concise title, then the complete unbounded body. The body contains the full point and every decision-record section exactly once, without nested record headings, proposal boilerplate, return-label metadata, or repeated lifecycle/ID metadata. Use `decision_ledger` action `detail` for one safely bounded tool record when needed; do not expand every record in a list. Use `/decisions export` when the user asks for the complete current-branch ledger; it includes every current item, title, full point, and all complete record fields, explicitly marks missing records, omits extension internals, and does not trigger a model turn. Ignored decisions remain dimmed and struck through and are shown last in ordered user-facing lists. This ordering is presentation-only: canonical item order, branch replay, and export completeness are unaffected. If `/tree` changes or removes the ledger, respect the selected branch; do not import state automatically. Use `/decisions recover` only after explicit interactive confirmation; it replaces the current branch ledger completely (it does not merge) with the newest recoverable off-branch snapshot.
